### 进程、线程、协程的区别？<Badge text="重要" type="danger" />

三者是**资源隔离粒度**从粗到细的三个层次。

| 维度 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 调度者 | 内核 | 内核 | 用户态运行时 |
| 地址空间 | 独立 | 共享所属进程 | 共享所属线程 |
| 切换成本 | 页表 + TLB 刷新，最高 | 寄存器 + 栈，中等 | 几个寄存器，最低 |
| 崩溃影响 | 互不影响 | 拖垮整个进程 | 取决于运行时实现 |
| 通信方式 | 管道 / 共享内存 / socket | 直接读写共享变量 | 同线程内直接传递 |

一句话概括：**进程是资源分配的单位，线程是内核调度的单位，协程是用户态调度的单位**。协程之所以快，是因为切换完全不进内核，也不需要内核态的锁；代价是一个协程里的阻塞系统调用会卡住整个承载线程，所以协程运行时必须把阻塞 IO 改写成事件驱动。

### 进程间通信有哪些方式？<Badge text="重要" type="danger" />

- **管道**：半双工、字节流。匿名管道只能用于有亲缘关系的进程；命名管道（FIFO）在文件系统里有名字，任意进程可用。
- **消息队列**：内核维护的链表，按消息为单位收发，天然有边界，可按类型选择性接收。
- **共享内存**：把同一块物理页映射到多个进程的地址空间，**最快**，因为数据不需要在内核和用户态之间拷贝；但必须自己配信号量做同步。
- **信号量**：本质是计数器，用于同步与互斥，而不是传数据。
- **信号**：异步通知，携带信息量极小，适合「通知发生了某件事」。
- **Socket**：唯一能跨主机的方式，本机内可用 Unix domain socket，比 TCP loopback 少一层协议栈。

::: tip 面试怎么答得漂亮
先按「传数据 / 做同步 / 发通知」分三类，再指出共享内存最快但需要额外同步、socket 唯一可跨机，最后落到自己项目里实际选了哪一种以及为什么。
:::

### select、poll、epoll 的区别？<Badge text="重要" type="danger" />

三者都是 IO 多路复用，差别在**如何告诉内核你关心哪些 fd，以及内核如何告诉你就绪了哪些**。

- `select`：用固定长度位图，默认上限 1024；每次调用都要把整个集合拷进内核，返回后还要 O(n) 遍历全部 fd 才知道谁就绪；集合会被内核改写，每次都得重设。
- `poll`：换成 `pollfd` 数组，去掉了数量上限，但拷贝和 O(n) 扫描依旧。
- `epoll`：`epoll_ctl` 注册一次常驻内核红黑树，就绪的 fd 由回调挂到就绪链表，`epoll_wait` 只返回就绪集合，**复杂度与总连接数无关，只与活跃连接数有关**。

::: warning 一个常见误解
「epoll 一定比 select 快」并不成立。连接数很少且几乎全部活跃时，epoll 维护红黑树和回调的开销可能反而更高。epoll 的优势场景是**海量连接、低活跃比例**，这正是长连接网关的典型形态。
:::

### 水平触发和边缘触发怎么选？<Badge text="掌握" type="tip" />

- **LT（水平触发）**：只要缓冲区里还有数据没读完，每次 `epoll_wait` 都会继续通知。编程模型宽松，可以一次只读一部分。
- **ET（边缘触发）**：只在状态**发生变化的那一刻**通知一次。必须循环读到 `EAGAIN` 把缓冲区读干，否则剩下的数据不会再触发通知，直接表现为「请求卡住」。

ET 减少了 `epoll_wait` 的唤醒次数，性能上限更高，但要求 fd 必须是非阻塞的，且读写都要处理 `EAGAIN`。Nginx 用 ET，Redis 用 LT——因为 Redis 的瓶颈不在事件通知上，用 LT 换取实现的简单可靠更划算。

### 什么是零拷贝？<Badge text="掌握" type="tip" />

传统「读文件再发网络」要经过 4 次拷贝、4 次上下文切换：磁盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡。其中中间两次 CPU 拷贝完全是浪费，因为应用根本没打算修改数据。

零拷贝就是**让数据不经过用户态**：

- `mmap + write`：把页缓存映射到用户空间，省掉一次 CPU 拷贝，仍有 3 次拷贝。
- `sendfile`：数据全程留在内核，配合网卡的 SG-DMA 能力可做到 **2 次 DMA 拷贝、0 次 CPU 拷贝**。
- `splice`：借助管道在两个 fd 之间搬运，不要求其中一端是文件。

Kafka 的高吞吐很大程度就来自日志文件直接用 `sendfile` 下发，以及顺序写带来的页缓存命中率。
