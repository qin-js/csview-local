### 为什么用 B+ 树而不是红黑树或哈希？<Badge text="重要" type="danger" />

索引的核心约束是**磁盘 IO 次数**，而不是比较次数。

- **红黑树 / AVL**：二叉结构，千万级数据树高 20+，每层一次随机 IO，完全不可接受。
- **哈希表**：等值查询 O(1) 很快，但**不支持范围查询和排序**，也无法利用最左前缀，`order by`、`>`、`between` 全部退化成全表扫描。
- **B 树**：多路平衡，树高降到 3~4，但每个节点都存数据，单页能放的键更少，树更高；且叶子之间没有链表，范围查询要回到上层跳转。
- **B+ 树**：非叶子节点只存键和指针，一个 16KB 页能放上千个键，**千万级数据树高仅 3**，即最多 3 次 IO；数据全在叶子且叶子用双向链表串联，范围查询和排序只需顺序扫描。

::: tip 一句话结论
B+ 树把「树高」压到 3 层以内换取极少的随机 IO，又用叶子链表把范围查询变成顺序 IO，这两点正好命中数据库的真实负载。
:::

### 聚簇索引和非聚簇索引的区别？<Badge text="重要" type="danger" />

InnoDB 里表本身就是一棵按主键组织的 B+ 树，这棵树叫**聚簇索引**，叶子节点直接存整行数据。

二级索引（普通索引、唯一索引、联合索引）的叶子存的是**索引列 + 主键值**，而不是整行。所以用二级索引查非索引列时，需要先在二级索引树拿到主键，再回聚簇索引树取整行，这就是**回表**。

由此推出两条实践：

1. **覆盖索引**：让查询要的列都落在索引里，`explain` 的 `Extra` 出现 `Using index`，直接省掉回表。
2. **主键要短且单调**：主键越长，每个二级索引叶子都跟着变大；主键随机（如 UUID）会让聚簇索引频繁页分裂，写入抖动。

### 最左前缀原则是什么？<Badge text="重要" type="danger" />

联合索引 `(a, b, c)` 的排序规则是**先按 a 排，a 相同再按 b 排，b 相同再按 c 排**。因此只有从最左列开始连续使用，才能利用索引的有序性。

| 查询条件 | 能用到的部分 |
| --- | --- |
| `a = 1` | a |
| `a = 1 and b = 2` | a, b |
| `a = 1 and c = 3` | a（c 无法跳过 b 定位） |
| `b = 2 and c = 3` | 用不上（缺最左列） |
| `a > 1 and b = 2` | a 用于范围定位，b 只能过滤 |
| `a = 1 order by b` | a 定位 + b 天然有序，免排序 |

::: warning 范围列会截断后续列
遇到 `>`、`<`、`between`、`like 'x%'` 之后，后面的列失去有序性，只能作为过滤条件。所以设计联合索引时把**等值列放前面、范围列放最后**。
:::

### 索引什么时候会失效？<Badge text="掌握" type="tip" />

- 在索引列上做**函数运算或算术运算**：`where year(created) = 2026`、`where id + 1 = 10`。
- **隐式类型转换**：`phone` 是 varchar 却写 `where phone = 13800000000`，等价于对列做 `CAST`。
- **字符集或排序规则不一致**的联表字段。
- `like '%xxx'` 前导通配，无法定位起点。
- `or` 连接的条件里有一侧没有索引。
- 优化器估算**走索引比全表扫更慢**时主动放弃，比如要取表中大部分行。

前三种都可以靠改写 SQL 解决：把运算移到常量侧、把字面量类型对齐、统一表结构。

### explain 里最该看哪几列？<Badge text="了解" type="info" />

- `type`：访问类型，从好到差 `const > eq_ref > ref > range > index > ALL`。出现 `ALL` 说明全表扫描。
- `key` / `key_len`：实际用了哪个索引、用了多长，可用来判断联合索引用到了几列。
- `rows`：预估扫描行数，和最终返回行数差距过大说明过滤性差。
- `Extra`：`Using index` 是覆盖索引（好）；`Using filesort` 需要额外排序；`Using temporary` 用了临时表，通常出现在 `group by` 与 `order by` 字段不一致时。
