### AOF 和 RDB 怎么选？<Badge text="重要" type="danger" />

- **RDB**：某一时刻的全量内存快照，二进制紧凑，恢复快，适合做备份和主从全量同步。缺点是两次快照之间的数据会丢，且 `bgsave` fork 时若写入密集会触发大量写时复制，内存翻倍风险。
- **AOF**：追加写命令日志，可读、可修补，丢失窗口取决于刷盘策略。缺点是体积大、恢复慢（要重放命令）。

三种刷盘策略：

| appendfsync | 落盘时机 | 最多丢多少 |
| --- | --- | --- |
| `always` | 每条命令都 fsync | 几乎不丢，最慢 |
| `everysec` | 每秒一次 | 1 秒，默认折中 |
| `no` | 交给操作系统 | 不可控，最快 |

::: tip 生产上的答案
两个都开：AOF 保证丢失窗口小，RDB 用于快速恢复和备份。Redis 4.0 之后支持**混合持久化**，AOF 重写时把当前内存以 RDB 格式写在文件头部，后续增量用命令追加，兼顾体积与恢复速度。
:::

### AOF 重写为什么不会阻塞主线程？<Badge text="掌握" type="tip" />

重写是**fork 子进程**完成的：子进程基于 fork 那一刻的内存镜像生成新的 AOF，主线程继续处理请求。期间新写入的命令会同时进「AOF 缓冲」和「AOF 重写缓冲」，子进程完成后主线程把重写缓冲追加到新文件末尾，再原子替换旧文件。

7.0 之后改成 Multi-Part AOF：重写期间新的增量直接写新的 incr 文件，靠 manifest 清单组织，彻底去掉了重写缓冲和末尾追加的开销。

### 过期键是怎么删除的？<Badge text="掌握" type="tip" />

Redis 用**惰性删除 + 定期抽样删除**组合，而不是给每个 key 起定时器（那样 CPU 开销太大）。

- **惰性**：访问某个 key 时才检查是否过期，过期则删并返回 nil。
- **定期**：每 100ms 从设了过期时间的字典里随机抽 20 个，删掉过期的；若过期比例超过 25% 就再来一轮，但有时间上限防止卡住主线程。

由此推出：**没被访问、也没被抽中的过期 key 会继续占内存**。所以内存淘汰策略是最后一道防线，`allkeys-lru`、`allkeys-lfu`、`volatile-ttl` 等按不同口径淘汰。热点数据长期驻留的场景 LFU 通常比 LRU 更合适，因为 LRU 会把偶发批量扫描进来的冷数据误判为热数据。
