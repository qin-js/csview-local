### 缓存穿透、击穿、雪崩分别怎么解决？<Badge text="重要" type="danger" />

三者的区别在于**「谁不存在」和「谁失效了」**。

| 问题 | 本质 | 主要手段 |
| --- | --- | --- |
| 穿透 | 查的数据**根本不存在**，缓存和数据库都没有，每次都落库 | 缓存空值 + 布隆过滤器 + 参数校验 |
| 击穿 | 某个**热点 key 过期瞬间**大量并发同时落库 | 互斥重建 + 逻辑过期 + 热点永不过期 |
| 雪崩 | **大批 key 同时过期**或 Redis 整体宕机 | 过期时间加随机抖动 + 多级缓存 + 熔断限流 + 集群高可用 |

**穿透**：缓存空对象要设短 TTL（比如 60 秒），否则数据后来真的写入了会一直读到空。布隆过滤器能拦住绝大多数不存在的 key，但它有误判率且**不支持删除**，需要用 counting bloom 或定期重建。

**击穿**：只让一个线程拿分布式锁去重建，其余线程短暂等待后重读缓存；或者干脆不设物理过期，value 里带一个逻辑过期时间，读到过期就先返回旧值、异步重建，牺牲一致性换可用性。

::: warning 别把三者混为一谈
面试里最常见的失分点是把「热点 key 过期」说成雪崩。判断标准很简单：**一个 key 出事是击穿，一批 key 出事是雪崩，数据压根不存在是穿透。**
:::

### 如何保证缓存和数据库的一致性？<Badge text="重要" type="danger" />

先明确目标：缓存是**最终一致**的旁路副本，追求强一致就不该用缓存。

主流做法是 **Cache Aside + 先更新数据库再删除缓存**：

- 读：先读缓存，命中返回；未命中读库，回填缓存。
- 写：更新数据库，然后**删除**缓存而不是更新缓存。

为什么是删除不是更新？因为并发写下两次更新的顺序无法保证，缓存可能留下旧值；而删除让下一次读去库里取最新值，天然收敛。为什么不是先删缓存再更新库？因为在删除与更新之间进来一个读请求，会把旧值重新回填。

::: tip 兜底手段
- **延迟双删**：更新库后删一次，隔几百毫秒再删一次，覆盖掉期间回填的旧值。
- **订阅 binlog**：用 Canal 之类订阅变更再删缓存，把「删缓存」从业务代码里解耦出去，失败可重试。
- **给缓存设 TTL**：任何方案都要有兜底过期，避免不一致永久存在。
:::

### 用 Redis 实现分布式锁要注意什么？<Badge text="重要" type="danger" />

最小可用版本是 `SET key uuid NX PX 30000`，一条命令同时完成「加锁 + 设过期」，避免加锁后进程崩溃导致死锁。但真正上线还要处理四件事：

1. **解锁必须校验持有者**：value 存唯一 uuid，删除前先比对，否则会删掉别人的锁。比对与删除必须原子，用 Lua：

```sql
-- 语义示意：Redis 中执行的 Lua 脚本
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

2. **业务超时**：执行时间超过 TTL 会导致锁提前释放。需要看门狗定期续期（Redisson 的做法），或把 TTL 设为业务耗时的数倍。
3. **可重入**：同一线程重复加锁应计数而不是自锁，用 hash 存 `threadId → count`。
4. **主从切换丢锁**：主节点写入后异步复制，宕机切换会丢锁。RedLock 试图用多个独立实例缓解，但争议很大；对正确性要求极高的场景应该用 etcd / ZooKeeper 这类基于共识的组件。

### 布隆过滤器为什么会有误判？<Badge text="掌握" type="tip" />

它是一个很长的位数组加 k 个哈希函数。写入时把 k 个哈希位置置 1；查询时看这 k 位是否**全为 1**。

- 全为 1 → 「可能存在」。因为这些位可能是别的 key 置上的，所以有**假阳性**。
- 有任意一位为 0 → 「一定不存在」。因为自己写过的话不可能有 0，所以**没有假阴性**。

这个不对称性正好适配缓存穿透：过滤器说「不存在」就可以直接拒绝，说「可能存在」才放行去查缓存和库。误判率随装载量上升，需要按预估容量和可接受误判率反算位数组长度与哈希个数。

### Redis 为什么快？<Badge text="掌握" type="tip" />

- **纯内存操作**，没有磁盘随机 IO。
- **单线程处理命令**，没有锁竞争和线程切换，也没有并发数据结构的复杂度。
- **IO 多路复用 + 事件循环**，一个线程管理海量连接。
- **高效数据结构**：SDS、ziplist/listpack、跳表、渐进式 rehash 的字典。
- **协议简单**：RESP 解析成本极低，还支持 pipeline 批量往返。

::: info 单线程的边界
「单线程」指的是**命令执行**这一个环节。Redis 4.0 起把大 key 释放、AOF 刷盘等放到后台线程；6.0 起网络读写也可以多线程，但命令执行仍然串行，因此原子性语义不变。
:::
