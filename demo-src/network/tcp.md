### TCP 的三次握手过程？<Badge text="重要" type="danger" />

![TCP 三次握手时序](img/tcp-handshake.svg)

三次握手的目的是**同步双方的初始序列号，并确认双向通路都可用**。

1. **第一次**：客户端发 `SYN=1, seq=x`，进入 `SYN_SENT`。此时客户端只知道自己能发。
2. **第二次**：服务端回 `SYN=1, ACK=1, seq=y, ack=x+1`，进入 `SYN_RCVD`。服务端由此知道「对方能发、自己能收」，并且把自己的初始序列号 `y` 告诉对方。
3. **第三次**：客户端发 `ACK=1, seq=x+1, ack=y+1`，双方进入 `ESTABLISHED`。服务端收到后才确认「自己能发、对方能收」。

::: tip 为什么两次不够
两次握手时服务端无法确认客户端的接收能力，也无法确认自己发出的初始序列号被对方收到。更关键的是：一个在网络里滞留很久的旧 `SYN` 到达服务端后，服务端会直接建立连接并一直等待数据，白白占用资源。第三次握手让客户端有机会用 `RST` 拒绝这个历史连接。
:::

### TCP 为什么挥手要四次？<Badge text="重要" type="danger" />

因为 TCP 是**全双工**的，两个方向的数据流要分别关闭。

- 客户端发 `FIN` 只表示「我没有数据要发了」，服务端可能还有数据没传完。
- 服务端先回 `ACK` 确认收到关闭请求，此时客户端到服务端的方向关闭，连接处于**半关闭**状态。
- 等服务端把剩余数据发完，才发自己的 `FIN`。
- 客户端回 `ACK`，并等待 `2MSL` 后彻底关闭。

`ACK` 和 `FIN` 之所以不能像握手那样合并，就是因为中间这段「服务端还在发数据」的时间不确定。如果服务端恰好没有数据要发，内核也可能把 `ACK` 和 `FIN` 合并，出现三次挥手。

### TIME_WAIT 为什么等 2MSL？<Badge text="掌握" type="tip" />

`MSL` 是报文最大生存时间，Linux 里通常取 30 秒，所以 `TIME_WAIT` 常见为 60 秒。等 `2MSL` 有两个原因：

| 原因 | 说明 |
| --- | --- |
| 保证最后一个 ACK 能到达 | 若这个 `ACK` 丢了，服务端会重发 `FIN`。等待期内客户端还能重发 `ACK`；直接关闭则会回 `RST`，让服务端异常结束。 |
| 让旧连接的报文自然消亡 | 等待 `2MSL` 后，本次连接产生的所有报文都已在网络中过期，不会串到用相同四元组的新连接里。 |

::: warning 线上常见问题
短连接压测时客户端会堆积大量 `TIME_WAIT`，耗尽本地端口。解决方向是改用长连接 / 连接池，而不是盲目打开 `tcp_tw_reuse`；`tcp_tw_recycle` 在 NAT 环境下会丢连接，且已在新内核中移除。
:::

### TCP 和 UDP 的区别？<Badge text="重要" type="danger" />

- **连接**：TCP 面向连接，先握手；UDP 无连接，直接发。
- **可靠性**：TCP 用序列号、确认应答、超时重传、拥塞控制保证不丢不重不乱序；UDP 尽最大努力交付。
- **传输形式**：TCP 是字节流，没有消息边界，因此有粘包问题；UDP 是数据报，一次收发对应一个完整报文。
- **开销**：TCP 首部 20~60 字节，UDP 固定 8 字节。
- **通信模式**：TCP 只能一对一；UDP 支持一对一、一对多、多对多，可做广播和组播。

选型上，需要完整正确的数据（文件、支付、网页）用 TCP；容忍少量丢失但要求低延迟（音视频、实时游戏状态同步、DNS 查询）用 UDP。

### 什么是粘包，怎么解决？<Badge text="掌握" type="tip" />

粘包不是 TCP 的 bug，而是**字节流没有消息边界**的必然结果：发送端的 Nagle 算法会合并小包，接收端的缓冲区也可能一次读出多条消息或半条消息。

三种常见的划分方式：

1. **固定长度**：每条消息定长，简单但浪费带宽。
2. **分隔符**：用 `\n` 之类的特殊字符切分，需要转义正文里的分隔符，Redis 的 RESP 协议走这条路。
3. **长度字段**：消息头写明正文长度，先读头再按长度读体，是最通用的做法。

```cpp
// 长度前缀 framing：先读 4 字节大端长度，再读正文
bool readFrame(int fd, std::string& out) {
    uint32_t be = 0;
    if (!readN(fd, &be, 4)) return false;
    uint32_t len = ntohl(be);
    if (len > kMaxFrame) return false;   // 防御异常长度导致的巨额分配
    out.resize(len);
    return len == 0 || readN(fd, out.data(), len);
}
```

### 拥塞控制的四个阶段？<Badge text="掌握" type="tip" />

拥塞控制解决的是「别把网络压垮」，和流量控制（别把接收方压垮）是两件事。

- **慢启动**：`cwnd` 从 1 个 MSS 开始，每收到一个 ACK 就加 1，整体呈指数增长，直到 `ssthresh`。
- **拥塞避免**：超过 `ssthresh` 后改为每个 RTT 只加 1，线性试探带宽上限。
- **快重传**：收到 3 个重复 ACK 就立刻重传那一个报文，不等超时定时器。
- **快恢复**：`ssthresh = cwnd / 2`，`cwnd = ssthresh`，直接进入拥塞避免，而不是退回慢启动。

::: info 超时与重复 ACK 的区别
超时重传说明网络可能严重拥塞，`cwnd` 会被打回 1 重新慢启动；而 3 个重复 ACK 说明后续报文还在到达，只是个别丢包，所以只做温和的减半。
:::
